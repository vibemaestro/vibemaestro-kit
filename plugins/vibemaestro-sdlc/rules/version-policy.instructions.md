description: "Only in a repo that publishes plugins from an export: no version in its manifests; a PR adds a .changes/ file; only a release writes one, as a CHANGELOG heading the export puts in the manifest"
---

1. No `version` key in a `plugin.json` or a marketplace entry, and a sibling dependency is the bare name: Claude Code then keys an install by the commit, so every change reaches it with no bump.
2. A PR that changes `plugins/<name>/` adds one `.changes/<slug>.md` (plugins, level patch|minor|major, one line; an optional `upgrade:` line when an existing user must do or will notice something on update; its name without the date no other change file's; optional `supersedes:` and `cancels:` lines naming, without the leading date and `.md`, every earlier change file this change replaces or undoes, since a public release states only the final behaviour) and writes no version anywhere: not a manifest, not a kb page. A pending change file is edited only to add or change its `upgrade:` line.
3. A plugin's version is its last public release, the first `## X.Y.Z` heading of its `CHANGELOG.md`; the first public release is 0.1.0 for each plugin.
4. Only two PRs add such a heading: a release PR (skill `release`; it ships every pending change file) and a hotfix PR into `release` (patch); `release.py cut` writes either, and nothing else moves.
5. Level: patch a fix, minor a feature, major a breaking change (a `CONTRACT.md` row removed or renamed); a 0.x plugin may break in a minor.
6. After either merges, an owner-signed baton moves `release` to it; then publish it your own way. The export writes each released version into its `plugin.json` and, on a sibling dependency, `>=` the sibling's version at the release that cut the plugin's version (the `Released together:` line `release.py cut` writes first in each section; `>=0.1.0` for a section with none), so an unchanged version keeps its manifest bytes; the tags `<plugin>--v<version>` live in the published repo only (never in the source repo: a dependency range would install the tagged commit instead of main).
7. A hotfix's back-merge PR comes from `backmerge/<sha12>` and merges with a merge commit (the merge guard's lane, or `kit:owner-merge`): never squash it or update its branch from main. Its head is the `release` tip, or, when it conflicts with main, one merge commit of the tip and main made from the tip (skill `release`); any other commit above the tip is refused.
