# BatonRun

BatonRun is the method vibemaestro uses for the actions that write outside the session and are more than a simple write: a flow of several writes on GitHub, a registry push, a change to the user's Claude Code settings, a deletion, a change on a live system. This document is the **standard**: the single source for what BatonRun is, how a run works, and where its limits are. Everything else points here:

- the skill `batonrun` ([`plugins/vibemaestro-sdlc/skills/batonrun/`](../skills/batonrun/SKILL.md)) holds the **operating instructions** for writing a baton: the commands, the parameters, the script skeleton, what `check` refuses, the exit codes, and keeping or changing a baton. This document ships in the installed plugin (`docs/batonrun.md` in the plugin root), but the skill keeps every instruction a session needs, the stop list included, so a session does not have to read it;
- the rule `batonrun` (`plugins/vibemaestro-sdlc/rules/batonrun.instructions.md`) is a **reminder** when a privileged command is typed directly: a simple write goes on, anything else becomes a run;
- the runner [`plugins/vibemaestro-sdlc/scripts/baton.py`](../scripts/baton.py) is the **machine**: when the code and this text disagree, the code is what runs, and the disagreement is a bug in one of them.

The measurements and lessons behind the design are in [`docs/research/batonrun.md`](../../../docs/research/batonrun.md). For the whole kit, start at the [README](../../../README.md).

## 1. What BatonRun is

### Definition

The owner is the person who owns the repository and signs the risky runs: working alone, that is you. A **run** is one action run of a repeated workflow: many commands or scripts in a fixed series, executed as one gated block. The session writes or picks the run, the machine checks and rehearses it, it is signed once, the session runs it, the machine post-checks it, undoes it on failure, and logs it. The owner is never handed command lines to type.

- **One run, one gate.** The series is shown, signed and run as a whole: the signature covers every step of it, so nothing in the series runs unsigned and nothing outside it runs signed.
- **A simple write is not a run.** A write that is one step, undone by one direct call that is not on the stop list, not on the stop list itself, and not a flow met before is a direct tool call: a comment on an issue, one new ticket. Everything else is a run: a flow of several writes, an act that cannot be undone (a merge, a push to a shared branch), an act the owner signs, and a flow met before. A flow cut into several simple writes is still a run (section 8).
- **A run is carried by one baton script.** The script holds the series; the commands and plugin scripts it calls are its steps (`kit:merge-pr` runs the merge guard; a session baton may run `open-pr.sh` as one of its writes). The script is the unit of checking and signing; the run is the unit of work and of the log.
- **Repeated is the point.** A workflow that recurs becomes a kept baton: one general script that declares its parameters, kept once with `baton pack` and called by name with new values (section 4). The next time it is one `baton go <place>:<name> key='value'…`, not a script written again.

### The name and the image

The image is the **conductor's baton**: only the session that runs the action holds it, and nothing plays until it is raised. The relay-race meaning is not intended. The method is BatonRun, the CLI is `baton`, one script is a baton script.

### Relation to CodeAct

CodeAct is an agent design from an ICML 2024 paper, also used by OpenHands' `CodeActAgent`. BatonRun keeps CodeAct's core: an action is code, not a JSON tool call, so several tools combine in one step with loops and branches, and the agent reads the output and fixes the script. The difference is where side effects may happen. OpenHands makes them harmless with a sandbox, so its loop is autonomous. A real cluster, registry, GitHub or user config cannot be sandboxed, so BatonRun has an inner loop with no consequences (write, check, rehearse, fix) and an outer gated step: one run of exactly the script that was signed.

### What BatonRun is not

- **Not a defence against a session that sets out to deceive.** It guards an honest but fallible session: a forgotten step, an edit after approval, other arguments, a world that changed, a second run. A session that writes a record by hand, runs a script with plain `bash`, copies `baton.py` elsewhere or builds a name at run time is forging; read-only tools and the owner's deny rules are what stop that (section 8).
- **Not a sandbox.** The writes are real. Rehearse shows the plan; it does not simulate the world.
- **Not a block on typed commands.** The rule reminds and the hook warns; neither refuses a command.
- **Not a place for secrets or credentials in the text.** A baton script, its plan lines and its log are plain text, so a credential does not belong in them.

## 3. The lifecycle

| Step | What happens | What it catches |
|---|---|---|
| write | the session finds a kept baton, kit or kind with `baton list`, or writes the baton script: header (Purpose, Targets, Blast, Undo, Pre, Stops, Params, Expect), the act with every change through `write()`, a post-check, an undo | the act stated before it runs |
| check | static checks of the text: header fields, `Params` and how the script reads its values, the exact `write()` gate and phase dispatch, `set -euo pipefail`, no write outside `write()`, no local script or `source`, no unguarded `diff`/`grep`/`cmp` in a pipeline, stop patterns against `Stops`, `bash -n`, `shellcheck -S error` where installed | syntax and shape errors, a write that would skip the gate, an undeclared stop act |
| rehearse | the values are checked against `Params`; the script runs in phase `rehearse`: every read runs, every write only prints its plan line; the plan is compared with Expect line by line, and each plan line with the declared Targets | logic errors, a wrong target, a missing precondition, a plan that is not what was meant |
| seal | the hash over script bytes, its place, the values (and each file value's sha256), directory, the variables that steer the tools, and the plan | any change after this point |
| sign | the seal is approved, by the session (`coordinator-auto`, only mode `auto` and `Stops: none`) or by the owner in a dialog | an approval of something other than what was shown |
| run | rehearse again, then phase `run`: each write's DO line must be the signed plan; the signature is used up | a world that moved since signing, a second run |
| post-check with undo | phase `postcheck` (read again after 1, 2, 4 and 8 s); on failure phase `undo`, which compares every target with its before-state | a write that did not hold; a half-done state left behind |
| log | one line per event in `log.tsv` (time, event, name, script hash, binding, arguments, directory, signer, mode, result, undone, output path); the full output under `runs/` | an unaudited act |

**`go`** runs the steps from check to log in one command and stops at the first that fails, with that step's exit code and whole output. When every step holds it prints one line, `go: ok — <n> writes — <run log>`, which is all the session reports. A run that needs the owner (a Stops word, or mode `manual`, also when no mode was chosen yet: section 6) stops after rehearse with exit 8 and the facts for the decision card; nothing is signed and nothing runs. The separate commands (`check`, `rehearse`, `sign`, `run`, `log`) stay for the owner's signature and for diagnosis.

`go` runs a session baton (and reads an `input` value, the `--spec` file of `kit:gh-write` and the rules file of `kind:settings-merge`) only from a file written in the last 120 s, so a Write that did not land is not mistaken for the new script; `go --reuse` names an older file whose bytes are meant again. A kept baton has no such gate: it runs only with the bytes its keep record pins. A session baton is a Write to a fresh path and `go <path>` in the same response. The form `go -` also exists, but it is not the way to run a baton, because Claude Code blocks a heredoc that holds the baton skeleton and a heredoc is the only way to feed it (section 8). It reads the script from stdin, stores it once under the state directory and runs that file, so the same sha256 binding holds from check to run.

### Commands

Each command is `<launcher> <subcommand> …`. Until the launcher is installed (section 9) use `python3 <plugin root>/scripts/baton.py` instead. The runner's own options come before the script; everything after it is the script's: `key='value'` words for a baton with `Params`, the flags or words its `Usage` shows for a kit or kind. A script is a path (a session baton), `kit:<name>`, `kind:<name>`, `project:<name>` or `user:<name>`; any other prefix, or a bare name, is refused.

| Command | What it does |
|---|---|
| `new <name> [--dir D] [--from <kind>]` | writes `D/<name>.sh` from the template, or from a kind (`new --from <kind>`); never overwrites (exit 6) |
| `check <script>` | the static checks of the text; exit 0 or 1 |
| `list [<keyword>…]` | one line per baton (`kit:`, `kind:`, `project:`, `user:`) whose name, Purpose or Params hold every keyword, at most 25: who signs, its runs, `reviewed` or `not reviewed, kept by …`, the Purpose and the Params or Usage; when one baton matches, or a keyword is the full name of exactly one of those that match (`kit:branch-delete`), its whole entry |
| `pack <path> <project\|user>:<name>` | keeps a script that ran ok: writes `<place>/<name>.sh` and a keep record that pins its sha256; a `user:` keep prints one `owner:` line for the owner. `pack <project\|user>:<name> <other place>:<name>` moves a kept baton. In a sandbox a bare `<name>` is `project:<name>` and `user:` is refused (section 4) |
| `pack --retire <project\|user>:<name> <sha256>` | unpins one sha256; the file stays |
| `rehearse <script> [args…]` | check, then the rehearse phase; prints the plan against Expect and the seal |
| `sign --by owner\|coordinator-auto --seal <seal> <script> [args…]` | check, the mode policy, rehearse again, then the signature record; `--by` comes first, once, as two words; a seal that is not the one shown is refused (exit 3); `--by owner` also needs the record the plugin's hook wrote when it opened the owner's dialog for that very call, else exit 3 |
| `sign --by owner --queued <id>` | the owner signs a queued item, in the session that queued it or another Claude Code session: the same hook, dialog and one-use record; the signature is written into the item (section 6) |
| `sign --by owner --approve <spec>` | the owner signs a plan in one dialog through the same hook and record: every row that is not dropped (a spec that still lists rows: those rows), each with its touches, the intent and the spec with their sha256 and the spec's acceptance criteria, read at the pinned commit; `kit:merge-pr` then merges up to each row's PRs, and `go --row` runs the batons a row declares (section 6) |
| `sign --by owner --charter <spec>` | the owner signs a focus charter in one dialog through the same hook and record: the focus read from the brain with its words, the repositories, kinds, maximum Stops and expiry it covers (section 6) |
| `run <script> [args…]` | the signed run: rehearse again, run, post-check, undo on failure; one line `run: ok — <n> writes — <run log>` when it holds |
| `sign --by owner --void <id or binding>` | the owner withdraws a queued item (pending or signed) or voids a signature that never ran, through the same hook and dialog, whose card shows the record; the item moves to `queue/withdrawn/`, the signature to `voided/`, bytes kept, and nothing runs them after; refused when used or its run has started (section 6) |
| `queue withdraw <id> --reason <word>` | the session that queued an unsigned item withdraws it (same session id or Claude Code process); kept and marked who, when and why, never signed or run after |
| `run --queued <id>` | the same run for a signed queued item, from the directory it was queued in, once, before it expires; the plan must equal the sealed one |
| `go [--by coordinator-auto \| --queue] [--reuse] <script> [args…]` | check, rehearse, seal, sign, run, post-check and log in one command; the lifecycle above. With `--queue`, a baton that needs the owner is queued for them instead of stopping at exit 8: one line names the item (section 6). `<script>` is a path, `kind:<name>`, `kit:<name>`, `project:<name>` or `user:<name>`. `go -` takes the script from stdin: never use it for a baton, Claude Code blocks it |
| `go --row [<owner/repo>:]kb/plans/<file>.md#<row> [--reuse] <baton> [args…]` | `go` for a `kit:` or `project:` baton; where `go` would stop at exit 8, a run touch of that row of the owner's plan approval, else of a plan of the focus of the owner's charter (the line naming its repository), covers the call, with no dialog: signed `plan:<approval or charter>/<row>/<n>` in that process, the use taken right before the run phase, and the one line ends with that signer (section 6). A `user:` baton, a session file, a `kind:`, stdin and a sandbox session are refused (exit 64) |
| `log [--tail N]` | the last N lines of `log.tsv` (default 20) |
| `log --last` | the path of the newest run log; it is set before the script starts, so a run that was killed is found here |
| `log --wait-names N1,N2,… [--timeout S] [--since T]` | waits (at most 580 s) until the latest run line of each named script is ok; exit 9 at the deadline |
| `log --queue` | the queued items: pending, signed, expired, used, withdrawn or damaged, each with its card and the next command |
| `log --wait-queued <id> [--timeout S]` | waits (default 580 s, at most 24 h) until the item is signed (exit 0); exit 3 when it can no longer be (expired, used, damaged, absent), 9 at the deadline |
| `log --grants` | each approval or charter: in force, expired, revoked, damaged or not in force, with its card and each row and how many of its pull requests merged; a record of another kind (a plan grant an earlier version wrote) is listed not in force, and nothing of it is read; `log --grants --json` prints the same grants as one JSON document, `{schema: 1, grants: [...]}`: each has `id`, `kind` (`approval`, `charter` or null), `state`, `reason`, `error` (true for a damaged or absent record, which has no other field), `signed_at`, `expires` and `dir`, an approval its `plans` ({repo, path, commit}) and `rows` ({plan, row, prs, merged}), a charter its `focus`, `repos`, `kinds` and `max_stops` |
| `log --digest [--since <N>h\|<N>d\|<UTC time>] [--plan <id>]` | what was done in the window (default 24 h) that the owner did not sign, grouped by plan approval: first the runs and merges under no approval, one line each (time, name, signer, result, undone), a count per signer and the approvals in force with their expiry; then each approval in force or with an act in the window: its state, each row's pull requests merged and each run touch's runs used (`(signs again)` for one it never covers), its merges (time, `kit:merge-pr`, signer `approval:<id>`, result `touches <repo>:<path>@<commit>#<row>`, `-`, then the pull request) and its runs (signer `plan:<id>/<row>/<n>`); last the owner's own signatures in the window by kind: plan dialogs, per-run (the merges through `kit:merge-pr` among them) and queued. A charter with an act or a hold line in the window has its own section, `charter <id>: <state> until <expiry>, focus <P>`, then its merges (signer `charter:<id>`), its runs (signer `plan:<id>/<row>/<n>`) and its hold lines. `--plan <id>`: that approval or charter alone, since it was signed unless `--since` says otherwise. A run that started and has no end line (killed, or still going) is listed with the result `unfinished`; a `refused` attempt is not a run, and a line whose time cannot be read is always listed |
| `grant revoke <id>` | ends an approval or a charter at once, for any session, with no dialog |
| `grant revoke --focus <P>` | ends each charter in force for that focus signed from this project; what the brain's `op close` or `op supersede` of the focus runs |
| `mode [manual\|auto]` | prints the approval mode, or sets it (section 6) |

| `permissions --install-launcher [--force]` | copies the launcher to `<state-dir>/bin/baton`; a cache copy the registry no longer lists refuses with exit 10 and writes nothing, unless `--force` |

### Exit codes

| Code | Meaning |
|---|---|
| 0 | done |
| 1 | the script fails check or rehearse (no verdict line, plan differs from Expect or the declared Targets), or `go` found a stale file or `input` value; `pack`: the source fails check as a kept baton |
| 2 | environment: no `bash`, or the state directory cannot be written; `pack`: a lock held 30 s |
| 3 | refused, nothing ran: no signature matches, the mode does not allow the signer, a run signed under the owner's window that no longer covers it, the command stopped before the run phase, or a kept baton is neither pinned on this machine nor reviewed (section 4); a queued item that is not signed, expired, used, damaged, or no longer matches; `log --wait-queued`: the item can no longer be signed; `sign --by owner --approve`: the approval changed since its dialog showed it; `sign --by owner --charter`: the charter (the spec, the focus's words or the directory) changed since its dialog showed it; `pack`: no ok run of these bytes, the bytes kept under another name, another Stops |
| 4 | the run or its post-check failed, and undo put the state back |
| 5 | the state is unknown: the run failed and undo failed too, or the run was interrupted (also an interrupted `pack`: the same command finishes it); tell the owner at once |
| 6 | `new`: the file already exists |
| 7 | `permissions --check`: a rule is missing, stale or unsafe |
| 8 | `go`: the baton needs the owner's signature; nothing was signed, nothing ran (a live window of the session's brain that does not cover the call adds `window: not lowered: <why>` to the card); `go --row`: the same, and no approval or charter covers the call (the first part that did not match is named) |
| 9 | `log --wait-names`: a named script has no ok run line by the deadline; `log --wait-queued`: the item is not signed by the deadline |
| 10 | `permissions --check`, or `--install-launcher` without `--force`: the session's vibemaestro-sdlc is not the installed one (it started before a plugin update); restart Claude Code; nothing written |
| 64 | bad usage: a call that does not fit the `Params` (a key missing, unknown or twice, a word with no `=`, a value that fails its type), an unknown prefix or a bare name; `pack`: no place outside a sandbox, `user:` in a sandbox, a kit, kind or copy name; `mode trust`: not a network remote; `go --queue` in a sandbox, with no session id, with `--by`, on a baton the session may sign itself, or on a baton whose `Stops` names `secrets`; `--queued` with a malformed id, another signer, or a word after the id; `--approve` with another signer, a relative path or a word after it, or a spec that breaks its rules; `--charter` with another signer, a relative path or a word after it; `grant revoke` with a malformed id, `grant revoke --focus` with a malformed focus; `go --grant` and `sign --grant` in any spelling (there are no plan grants: a run the session may not sign stops for the owner); `go --row` with a malformed plan line, with `--by` or `--queue`, in a sandbox, or for a `user:` baton, a session file, a `kind:` or stdin; `log --digest --plan` with a malformed id |
| 65 | `sign --by owner --charter`: the charter spec breaks a rule, each named: its five keys, the repositories, a kind outside the four, `owner-acts` or a `SIGN_AGAIN_STOPS` word in `max_stops`, the expiry; the focus is closed, unknown or has no `done when`; or a charter for that focus is in force from this project (named) |
| 66 | the script cannot be read (no such kept baton, no project root), `log --last` before any run has started, `pack --retire` with no record of the sha, or `grant revoke` or `log --digest --plan` of no such approval or charter |

### The header

Every baton script starts with these fields, one line each. `check` refuses a missing field, a field given twice and an empty `Expect`; `Each` is for kit scripts only and stands in for the `Expect` lines. A baton declares `Params` or, a kit or callable kind only, `Usage`; a kept baton declares `Params` with at least one key.

| Field | What it says |
|---|---|
| `Purpose` | what the run does, in one sentence; a session searches this line when it looks for a kept run |
| `Targets` | what it touches; in a baton with `Params`, patterns before ` — ` (`{dest}`, `{dir}/**`, `{repo}#{issue}`, `{ns}/{pod}`), then prose: every plan line names at least one, and each of its absolute-path, repository, URL or `refs/` words matches one (the copies of file values are exempt; a word such as `--to=/x` is not read as a path, so write a path as a word of its own). Targets that do not read as patterns are not tested, and `pack` refuses them |
| `Blast` | the most it can change |
| `Undo` | how it is put back, or what it leaves behind |
| `Pre` | what must hold before it runs |
| `Stops` | `none`, or one or more stop-list words (section 6); the owner signs when it is not `none` |
| `Params` | `none`, or `key=type` words: `int`, `sha40`, `sha256`, `name`, `repo`, `ref`, `path` (absolute), `url` (https), `file` (an existing file), `input` (a file written for this call), `under:<dir>`, `enum:<a>\|<b>`. Every key is required and given once. No value holds a space, a quote or `$`, so free text (a title, a body) is an `input` file. The script reads the values once, in a block of `P_<KEY>="$<n>"` lines in the declared order; a file value arrives as a read-only copy. A secret (a private key, a token, a cluster credential) is a `path` value, which the script feeds to a command's stdin and never prints: a `file` or `input` value is copied under the state directory (a call that never reaches its run phase removes its copy when it ends, unless another baton process holds it; the copy a run used is kept, the newest 200, until a later call of the same bytes that never runs ends), so one that looks like key material (a private-key header, a `client-key-data` field, a token of a known shape) is refused (exit 64) |
| `Usage` | kits and callable kinds only: the synopsis of their flags or words |
| `Expect` | one line per write, a shell glob over the whole plan line, in order (below) |
| `Each` | kit scripts only: one glob for every plan line, for a run whose number of writes comes from its input (`kit:gh-write`) |

**How Expect matches.** Rehearse collects one plan line per `write()` call, in the order they ran, and compares the i-th with the i-th `Expect` line as a shell glob over the whole line, case-sensitive. `*` is any run of characters (spaces and `/` too), `?` one character. It is not a prefix match, and the counts must be equal: a missing or an extra line is a FAIL row. For example the plan `create docs/a b.txt` matches `create *`; the plan `create docs/a.txt` does not match `create`.

### The skeleton

A baton script that passes `check`, and `pack` once it ran ok. Replace the header, the values block, the act, the post-check and the undo; copy `write()`, `gh_state()` and the final `case` unchanged. To ask whether a GitHub object exists, call `gh_state <api path>` as a statement, then test `$GH_STATE` (`exists` or `absent`; anything else stops the script).

```bash
#!/usr/bin/env bash
# Purpose: create one file holding the bytes of an input file
# Targets: {dest} — the file dest names
# Blast: that one file
# Undo: removes the file while it holds those bytes
# Pre: the file is absent
# Stops: none
# Params: dest=path body=input
# Expect: create *
set -euo pipefail
PHASE=${BATON_PHASE:-rehearse}
write() {
  local plan=$1
  shift
  case "$PHASE" in
    rehearse)
      printf 'PLAN %s\n' "$plan"
      printf '%s\n' "$plan" >> "${BATON_WRITES:-/dev/null}"
      ;;
    run | undo)
      printf 'DO %s\n' "$plan"
      printf '%s\n' "$plan" >> "${BATON_WRITES:-/dev/null}"
      "$@"
      ;;
    *)
      printf 'write called in phase %s: %s\n' "$PHASE" "$plan" >&2
      return 70
      ;;
  esac
}
gh_state() {
  local out rc=0 proto code
  out=$(gh api --include "$1") || rc=$?
  read -r proto code _ <<< "${out%%$'\n'*}"
  case "$rc $proto ${code%$'\r'}" in
    "0 HTTP/"*" 200") GH_STATE=exists ;;
    [1-9]*" HTTP/"*" 404") GH_STATE=absent ;;
    *)
      echo "gh_state $1: exit $rc: $proto $code" >&2
      exit 75
      ;;
  esac
}
P_DEST="$1"
P_BODY="$2"
holds() { [ -f "$P_DEST" ] && cmp -s "$P_DEST" "$P_BODY"; }
put() { cat -- "$P_BODY" > "$P_DEST"; }
act() {
  [ ! -e "$P_DEST" ] || { echo "REFUSE $P_DEST exists" >&2; return 3; }
  write "create $P_DEST" put
}
postcheck() { holds; }
undo() {
  if holds; then
    write "remove $P_DEST" rm -f -- "$P_DEST"
  fi
  ! holds
}
case "$PHASE" in
  rehearse) act; echo "VERDICT rehearse ok" ;;
  run) act; echo "VERDICT run ok" ;;
  postcheck) postcheck; echo "VERDICT postcheck ok" ;;
  undo) undo; echo "VERDICT undo ok" ;;
  *) echo "unknown phase: $PHASE" >&2; exit 64 ;;
esac
```

### Try it

This runs the skeleton end to end in a scratch state directory and keeps it. Run it in bash, from the root of a checkout of this repository, in one shell session. Save the skeleton above as `demo.sh` in the scratch directory, then run `go` within 120 s of saving it and of writing the input file (or add `--reuse`).

```bash

export XDG_STATE_HOME="$(mktemp -d)" XDG_DATA_HOME="$(mktemp -d)"
DEMO="$(mktemp -d)"
# save the skeleton as "$DEMO/demo.sh", then:

$BATON check demo.sh
$BATON rehearse demo.sh dest="$DEMO/out.txt" body="$DEMO/body.txt"
mkdir -p "$XDG_STATE_HOME/vibemaestro/baton" && printf 'auto\ndialog %032d\n' 0 > "$XDG_STATE_HOME/vibemaestro/baton/mode"   # the scratch state only: a real mode change is the owner's click (modes)
$BATON go demo.sh dest="$DEMO/out.txt" body="$DEMO/body.txt"

```

`XDG_STATE_HOME` and `XDG_DATA_HOME` point the mode, the signatures, the log and the library at throw-away directories, so the demo never changes your real approval mode or library. After `mode auto` the session may sign this `Stops: none` run itself, so `go` ends with one `go: ok` line and `out.txt` holds `hello`. In mode `manual` the same `go` stops after rehearse with exit 8 and the owner's decision card. `pack` keeps the script as `user:demo-put` and prints its `owner:` line; from then on `go user:demo-put dest=… body=…` runs it with other values.

## 4. When a workflow becomes a run, and where runs live

**A simple write is direct.** One step, undone by one direct call that is not on the stop list, not on the stop list itself, not a flow met before: the session makes the tool call. Anything else is a run, and the session looks for one before it writes one:

1. `baton list <keyword>`.
2. **One fits** (the same purpose, targets and risk): `baton go <place>:<name> key='value'…`, every value single-quoted, since the session's command line is a shell. Free text that came from outside (an issue title, a message) goes into an `input` file the session writes, never onto the command line.
3. **One is close:** evolve it in place (below), never a copy.
4. **None fits:** write it as a session baton with `Params`, run it, and the second time the flow is met, keep it with `baton pack`.

**Where runs live.**

| Run | Lives in | Run as |
|---|---|---|
| kit run | `plugins/vibemaestro-sdlc/batons/<name>.sh` (versioned plugin code; the gates it runs are in `gates/`) | `<launcher> go kit:<name> …` |
| kind | `plugins/vibemaestro-sdlc/templates/baton-kinds/` | `<launcher> go kind:<name> <args>` |
| dependent plugin's run | that plugin's `batons/` (a plugin of the same marketplace that depends on `vibemaestro-sdlc`) | `<launcher> go kit:<name> …` (`help kits`: how it is found and trusted) |
| project baton | `<project root>/.vibemaestro/batons/<name>.sh`, committed with the repository and reviewed in its pull request | `<launcher> go project:<name> key='value'…` |
| user baton | `$XDG_DATA_HOME/vibemaestro/batons/`, else `~/.local/share/vibemaestro/batons/`: this machine's library, outside every repository | `<launcher> go user:<name> key='value'…` |
| session baton | a fresh path the session writes (a scratch directory); never stdin (`go -` with a baton heredoc is blocked, section 8) | `<launcher> go <path> …` |

A call always names the place; there is no lookup across places, so nothing in a repository or the library can stand in for a `kit:` or `kind:` baton.

**Keeping: `baton pack`.** `pack <path> project:<name>` or `pack <path> user:<name>` keeps a session baton that ran ok. It refuses a script with no `ok` run of these exact bytes in the log, one that fails `check` as a kept baton (it needs `Params` with at least one key and `Targets` as patterns), the same bytes already kept under another name, a name already kept with another `Stops`, a `kit:` or `kind:` name and a copy name (`-v<digits>`, `-<7 or more hex>`). It writes the file and a keep record in the state directory that pins the sha256: a kept baton runs only with pinned bytes, at every step, so a file changed by hand is not callable until it is kept again. `pack` does not commit; a project baton is committed on the branch and reviewed in its pull request. A user baton is reviewed by nobody: `list`, the sign line, `go`'s success line and the decision card say `not reviewed, kept by …`, and each `user:` keep, new or evolved, prints one line starting `owner:` that the session copies into its next reply to the owner. `pack --retire <place>:<name> <sha256>` unpins one sha; `pack project:<name> user:<name>` (or the other way) moves a kept baton.

**In a sandbox.** A session in a sandbox pod (`VIBEMAESTRO_ROLE=worker`, or, deprecated and leaving in the next release, `INTENT_SLUG` and `SEAT` both set) keeps to `project:`: `pack <path> <name>` keeps `project:<name>`, and a `user:` keep or a move to `user:` is refused (exit 64), since the pod's library is lost with the pod. A pod never gets the owner's signature, so a flow that stops for the owner is handed to whoever briefed the session (a person, or a session that hands out work):

1. The session runs `go <path> key='value'…` up to the owner's decision card (exit 8): check, rehearse and the plan against Expect and the Targets all held. In a sandbox, that stop is logged for these exact bytes when it comes from the baton's `Stops`, or from mode `manual` for a session script (a path) with `Stops: none`, and the output names the call to hand over instead of a sign line, under a name that whoever briefed the session can run: no sign, `run` or `go --queue` is a next step there, and no mode command is shown. A session script without `Params` is told the one step first: add them, then `go` again. `rehearse` in a pod names no owner command either: its last line says that `go` hands the call over.
2. `pack <path> <name>` keeps those bytes as `project:<name>` on that logged stop instead of an `ok` run; its line says `not run: stop-list, the owner signs after merge`. A `Stops: none` script keeps only on a stop logged in mode `manual`: its line, its keep record and the hand-off say it never ran, so the `go` of whoever briefed the session is its first run. Only in a sandbox and only to `project:`; everywhere else `pack` needs an `ok` run.
3. The session commits the baton on its branch, opens the pull request and tells whoever briefed it the call.
4. Whoever briefed it merges it after a post-check, then runs it from a session with the owner's signature, or, for a kept `Stops: none` script that never ran, with that session's own signature (`coordinator-auto`) when the mode of that machine is `auto` (its first run): as `project:<name>` from a checkout of the merged default branch when that repository's remote is on the owner's remote list (below), else from a fresh scratch copy of the merged file, which it then keeps with `pack`.

**Merging a project baton.** The default deny globs that `kb.py init` writes, and that the guarded merge adds to a repository's first pull request, deny `.vibemaestro/*` (the config), `.vibemaestro/gates/**` and `.vibemaestro/rules/**`, and leave `.vibemaestro/batons/` to the guard like other code. A repository whose `merge.deny_globs` names `.vibemaestro/**` keeps every project baton an owner merge.

**Reviewed project batons.** A `project:` baton runs without a keep record on this machine when all hold, checked at every step as the pin is: the project root is in git; `refs/remotes/origin/HEAD` names a branch of origin; origin's URL, in its canonical form (`host/path`: no scheme, userinfo or `.git`, the host in lower case), is on the owner's remote list; and its bytes, as a git blob, are the blob at its path on that branch. Its label is then `reviewed on <url> <branch>`. The list lives in the state directory, outside every repository, and is empty until the owner sets it: `mode remotes` prints it, `mode trust <remote>` and `mode untrust <remote>` change it, each with the owner's dialog as for the mode. A remote written with a user or token before `@` (git's own `git@host:path` aside) is refused (exit 64): write it without one. A file changed on a branch, a baton only on another branch, a link on origin, a retired sha, a remote not on the list (a relative path, or a URL ending in `/.git`, is never one), a project root that is not the top of its repository and a `user:` baton all need a keep record; the refusal (exit 3) says which condition failed.

**A kept baton is not trusted code.** Every call runs check, rehearse, the plan against Expect and the Targets, seal, sign, run, post-check and log, like a session baton. It may not run a gate, holds no secret, and its `Stops:` decides who signs; in mode `auto` the session may sign a `Stops: none` baton another session kept.

**Naming and finding.** A baton has a short kebab-case name that says what it does (`merge-pr`, `gh-write`, `ci-rerun-failed`), and its `Purpose:` header line says it in one sentence. `baton list <keyword>…` finds it: one line per baton whose name, Purpose or Params hold every keyword, at most 25, and the whole entry when one baton matches. A session that hands several runs to a subagent names them `<prefix>-<act>.sh` with a prefix of its own, so `log --wait-names` can wait for exactly those names.

**A run that was killed.** `run` and `go` print one line when they hold, so a run killed before it ends (SIGKILL, a tool timeout) prints nothing. Before the script starts, the runner writes a `run-start` line to `log.tsv` and the run log's path to `runs/LAST`; `<launcher> log --last` prints that path.

**From a kept baton to a kit.** A baton other repositories need becomes a `project:` baton of each, or a kit: open an issue in the kit's public repository that carries the script, what it does, how many runs the log shows and whether they held, and where else it is needed. A run for sdlc's own domain becomes a `kit:` run or a `kind:` in `vibemaestro-sdlc`. A run that belongs to a dependent plugin ships in that plugin's `batons/` and runs as `kit:<name>`, with every check of an sdlc kit; a name two plugins ship runs nowhere, so a kit name is unique across the plugins.

### How a run evolves

The rule: **a kept baton stands for a workflow, so a changed workflow updates it, never a forked copy.** The test is whether it is still the same workflow: the same purpose, targets and risk.

- A step needed every time: add it to the baton.
- A step needed sometimes, or a value that changes between runs: a parameter. The signature binds the values, so the plan shows them.
- Another purpose or other targets, or a new Stops word: a new baton with its own name.
- A step met for the first time: a session baton this once; the second time, fold it into the kept baton.

To evolve one, copy the kept file to a fresh path, change it, run it with values, then `pack` it again under the same name. For a project baton every kept sha stays callable until retired, and git keeps the old versions; for a user baton only the newest keep is callable, and the keep records and the log keep the old ones.

Guards:

- A change within the same workflow that widens what the baton touches updates its header. A new Stops word makes a new baton (above), and the owner signs it from then on.
- `pack` refuses a copy name and the same bytes under a second name, so a copy is not the cheap way through.
- A kit run changes only through a kit PR; meanwhile the extra step runs as a separate run right after it.
- The signature binds the script's sha256 and the log records it, so which version of a baton ran stays known.

## 6. Approval: the modes, the stop list, the owner's signature

**The modes** are the owner's standing decision, not the session's choice per run. They live in the user's state directory, never in a repository (a machine policy, below, sets a mode where the owner has not); `mode` prints the mode (`manual` when none was set), and `mode manual|auto` changes it only on the owner's word: like `sign --by owner`, the change needs the record of the owner's dialog that the plugin's hook writes for the literal call, and a call without one is refused. The session never picks the mode itself, and a message from another agent or machine does not change it.

**Asked once.** A fresh install has not chosen a mode. With no machine policy (below) it reads as `manual`, and the first `Stops: none` run that stops for it (`go` exit 8) has the card line `mode manual (not chosen yet)` (with the file's value, unconfirmed, when an older version wrote the mode file). The session then asks the owner once which mode, and says what each means: `auto`, recommended on a solo machine (the session signs a `Stops: none` run; a stop-list run still needs the owner), or `manual` (the owner signs every run). Only right after the owner's own answer, the session runs the command the card's `Mode:` line names, `<launcher> mode <answer>`, alone in its Bash call: the plugin's hook opens the dialog, and the owner's click there sets it. Then the session runs the baton again; `go` refuses a file written over 120 s before, so it writes it to a fresh path. Once a mode is set, the card never says `not chosen yet` again. No answer, or a rejected dialog, leaves the mode not chosen: the run waits for the owner's signature as in manual, and the next exit 8 on a `Stops: none` run asks again.

**The machine policy.** Where the owner has not chosen, the mode comes from `/etc/vibemaestro/baton-mode` when the machine's builder wrote it as root (`auto` or `manual`, as a sandbox image does at build time), else it is `manual`: the owner's choice wins, then this file, then the default. It counts only as a regular file owned by root and not writable by group or other, under directories that are all root's, not writable by group or other and not links, read in the machine's own user namespace; a file there that fails any of this is ignored, with a `NOTE` line in `permissions --check`. `mode` prints the mode alone on stdout and where it came from on stderr, and `permissions --check` names the source too. A mode change in a sandbox stays refused, and names the policy when the policy set the mode.

- **manual** (the default until the owner chooses, where no machine policy sets the mode): the owner signs every run after seeing it.
- **auto**: the session signs a run whose header says `Stops: none` itself (`coordinator-auto`) and runs it with no question, a kept baton another session kept included (its sign line says `not reviewed, kept by …`); a run with any Stops word needs the owner's signature, as in manual.
- In auto, a failed precondition or an Expect mismatch is not a stop: the session fixes the script and rehearses again, as long as the fix does not widen what the run touches. A fix that widens it needs the owner.

**The stop list.** A run that does any of these declares it in `Stops:`, and then only the owner signs, in every mode:

| Word | The run … |
|---|---|
| `irreversible-delete` | deletes data that cannot come back: volumes with data, namespaces, package versions, repositories, branches and tags (check cannot prove a branch merged, so a hand-written branch or tag delete needs the owner; a merged branch of a GitHub repository goes through `kit:branch-delete`, one a local clone holds whole through `kit:branch-delete-recoverable`), secret paths, databases |
| `secrets` | reads, prints, writes or rotates a secret |
| `security-boundary` | widens a boundary: RBAC, admission or network policy, making something public, an admin bypass outside an existing owner rule |
| `cluster-lane` | changes a live cluster outside an approved lane: suspending reconciliation, draining nodes |
| `history-rewrite` | force-pushes or rewrites history on a shared branch |
| `money-org` | touches billing, plans or organisation admin (create or rename a repository, members) |
| `publish` | posts outside: public places, other people's repositories |
| `no-way-back` | can be neither rehearsed nor undone |
| `owner-acts` | is an act an earlier owner decision names the owner as the one who does |
| `recoverable-delete` | deletes what the baton first keeps a verified copy of, which undo puts back: a branch whose head `kit:branch-delete-recoverable` bundled into the state directory. Only a `kit:` baton declares it, since its reviewed code keeps the copy (`check` refuses it in a session, `kind:`, `project:` or `user:` baton, and refuses any other baton whose code holds the literal path `baton/bundles`: a text check, which a glob, a variable or a parent directory gets past). The copy guards against slips as the signature records do, not against a process of the same user that deletes it |

A call whose argument or Param value names a Claude Code settings file (a `settings*.json` right in a `.claude` directory, the managed settings directory or `$CLAUDE_CONFIG_DIR`), or such a directory itself, or another name of one (a hard link, the file or directory a settings link points to, unless that is a device or, behind a file name, a directory), is `security-boundary` whatever its `Stops:` says. `go`, `rehearse`, `sign` and `run` decide on the bound value, not the text: `~`, `$VAR`, `..`, a relative path, a link and a glob are resolved, and the part after an `=` is read too. Only the owner signs it: `go` stops with exit 8, `sign --by coordinator-auto` and the `run` of such a signature are refused, each naming the argument in one line. A value is read as one path, never searched for a path among other words, and a subdirectory of `.claude` is not one. A regular file with other hard links that baton cannot place counts too: its other name may be a settings file in a `.claude` no search reaches, so the owner signs.

`check` flags a body line that looks like a stop act, naming the category, the word and the header to add; that lint is a backstop, not a proof: a run declares what it does, not what the lint finds. The lint knows only some cluster acts (`flux suspend`, `kubectl … drain|cordon`).

**Who signs, at merge.** A pull request that changes who signs is an owner merge, whatever its other checks say. The gate `gates/signing_rules.py` (job `signing-rules`, named in `merge.required_checks`, so `kit:merge-pr` leaves a red pull request to the owner) is red when the pull request changes a baton's `Stops:` as `stops_of` reads them (a reorder or a space is no change), adds a file under a `batons/` or `templates/baton-kinds/` directory (case ignored), adds a symlink or a submodule anywhere (one can stand in for a baton directory), or changes a list that decides who signs: `STOP_WORDS`, what a plan never covers (`SIGN_AGAIN_STOPS`, `PLAN_SECRETS_KITS`), `MERGE_DENY_DEFAULT`, the header parser `stops_of` reads, the paths batons and kinds load from (`KIT_ROOT`, `KINDS_DIR`, `KINDS_REAL`), the plan approval's and the focus charter's limits (`APPROVAL_LIFE_MAX`, `CHARTER_LIFE_MAX`), what a charter may hold (`CHARTER_KINDS`), what an owner's window never lowers and how long it may last (`WINDOW_NEVER`, `WINDOW_NEVER_BATONS`, `WINDOW_LIFE_MAX`, `WINDOW_FLOOR_PATHS`, `WINDOW_FLOOR_PREFIXES`, `WINDOW_FLOOR_BATON_DIRS`), the touch kinds and the path table that give a change its kind (`kb_plan.py`), or the gate and its job. A list counts as changed when a statement of its file that uses it other than as a plain read changes (a binding, a mutation, an alias, an argument of a function that is not a pure builtin, its name as a keyword, attribute or string), when a statement that reaches names at run time changes (`exec`, `globals()`, `setattr`, `sys.modules`), or when a top-level name its definition reads changes. The pull request is judged by the list on its base, so editing the list does not help: that edit is red too. Another line of a baton, a deleted baton, a plain read of a list (`if w in STOP_WORDS`, `len(STOP_WORDS)`) and a condition (`allowed()`, the merge guard) pass it: it is a tripwire for slips, like the rest of baton, and the review is the gate for code. Another repository adopts it with its own list, a JSON file `{"baton_dirs": […], "lists": {"<path>": ["<name>", …]}, "files": […]}` passed as `signing_rules.py <base> <head> --list <file>` and read at the base, a job that runs it from a checkout of the base, and `signing-rules` in its own `merge.required_checks`. That way a repository whose session merges its own pull requests gets the same guard. With `--touches <file>` the gate also writes its causes for the merge guard's `touches` (below), once every cause is judged: `trust-touches v1`, one JSON line `[kind, path, object, stops]` per cause, `end <n>`; a Stops change or a new baton is kind `baton` with the head's Stops, every other cause `other`. The kit's job keeps that file as the artifact `trust-touches` of its workflow run.

**Owner merges.** A pull request the guarded merge refuses by design (a path `merge.deny_globs` denies, a new baton, a `signing-rules` red the plan marks `(signs again)`) is the owner's merge, through `kit:owner-merge`. The session post-checks each pull request (its head, CI, the changed files), runs `go kit:owner-merge <owner/repo> <pr> <head> [options] …` once for all of them, and shows the decision card, one line per pull request; the owner signs one `sign --by owner --seal …` dialog, and one `run` merges them all, then post-checks each one merged at its head. A sitting of several owner merges is one run: one card, one dialog. Each option belongs to the pull request before it, so the accepted reds, the required image and the admin bypass are each pull request's own, and a check name with a space or a parenthesis is percent-encoded (`internal-term%20scan`), since the owner's dialog takes plain words only; the card shows it decoded. A later pull request of the same repository merges once GitHub reports it mergeable after the earlier merge. A stop keeps the merges before it: the run's output and its undo name each one, the result says the state is unknown, and the way back is a revert pull request each, told to the owner.

**A settings change outside a baton is denied.** Adding a permission rule is `security-boundary`, and a session could make it with a plain tool, outside any baton. The plugin's hook `settings-guard.py` runs before every Edit, Write, MultiEdit, NotebookEdit and Bash call, in every mode, on the owner's laptop as in a pod, whatever the repository's `hooks` setting says. It looks at a Claude Code settings file: a `settings*.json` in a `.claude` directory or in `$CLAUDE_CONFIG_DIR`, the name's case ignored, through a symbolic or a hard link too, and the file a settings link points to.

- **Edit, Write, MultiEdit** are judged on the exact file after the call. Denied: an allow rule or an additional directory added; an ask or deny rule removed; `defaultMode` moved up the order `plan`, `dontAsk`, `default`, `acceptEdits`, `auto`, `bypassPermissions` (an unknown value counts as the top); `disableBypassPermissionsMode: "disable"` dropped; any other `permissions` key changed; a file left that is not a JSON object; any top-level key changed except `$schema`, `model`, `outputStyle`, `attribution`, `includeCoAuthoredBy`, `cleanupPeriodDays`, `language`, `alwaysThinkingEnabled`, `spinnerTipsEnabled` and `theme`. So `hooks`, `env`, `statusLine`, `apiKeyHelper`, the MCP keys, `enabledPlugins`, `sandbox`, `disableAllHooks` and every key Claude Code adds later are denied. A narrowing passes: an allow rule or an additional directory removed, an ask or deny rule added, `defaultMode` moved down. An Edit that does not match the file exactly is denied too (Claude Code's Edit matches more loosely, so the result cannot be known).
- **NotebookEdit** on a settings file is denied.
- **Bash** is judged on the command text, so every write the hook finds onto a settings name is denied, a narrowing included: a redirection, `tee`, `sponge`, `cp`, `install` or `rsync` onto it, a copy, move or link of a settings-named file into a `.claude` directory (`-t` too), `mv`, `ln`, `rm`, `truncate`, `dd of=`, `patch`, an in-place `sed`, `perl`, `awk` or `yq`, an editor, `git checkout|restore|rm|mv|stash` naming it, `curl -o`, `wget -O`, `find -delete` or `-exec` of a writer, `xargs` of a writer, inline interpreter code (`python -c`, a heredoc, `node -e`) that names it and writes. The hook splits words as the shell does, so a quoted sentence (a commit message) is one word and names nothing. The first word is the command; after a runner (`sudo`, `timeout`, `env`, `xargs`, `find -exec` and the like) any later writer word counts too. A string a shell runs (`bash -c`, `eval`, `su -c`, `$(…)`, backticks, a heredoc fed to a shell, a string literal in inline interpreter code) is read again as commands; any other heredoc body is data. Only a file whose own directory is `.claude` counts (a `.claude/worktrees/…` checkout above it does not). Reads pass.

The one way is `<launcher> go kind:settings-merge <settings.json> <rules.json>`: it adds allow, ask and deny rules, takes out the rules a `remove` object of the rules file names (every copy, any of the three lists), and stops for the owner (exit 8). On the owner's laptop too, a settings change goes through the kind, so the owner signs it. A change the kind does not make (`defaultMode`, another key) waits for the owner. In a pod the owner never signs: after exit 8 the session hands the call the output names to whoever briefed it, and the deny message says so. A baton's writes run inside its own process, which no hook sees, so `kind:settings-merge` and `kit:bootstrap` are not stopped. What the hook cannot see is in section 8.

**The owner's signature** is the owner's click in a dialog: right after the decision card the session runs `sign --by owner --seal <seal> …` alone in its Bash call, the plugin's hook makes that command ask whatever the permission rules say, and the dialog shows it. The hook writes a one-use record for that call, and `sign` refuses without it. The hook denies the call where no owner answers the dialog: in a sandbox, from a subagent, in a mode or a `-p` run with no dialog, while a hook or a permission-prompt tool could answer. The owner signs inside a `claude` session in a terminal, in Claude Code's VS Code extension or in the Claude desktop app (a plain shell has no Claude Code session, so no dialog): the two show the dialog in their own window, so their click is the owner's. On macOS the desktop app starts its Claude Code through a launcher of its own bundle that repeats Claude Code's command line; that one launcher, directly above Claude Code and inside the app bundle of the process that started it, is read as part of the app; any other process that carries a prompt tool is not. This holds on Linux and macOS; on Windows the owner's dialog and signed runs do not run yet, and each says so in one line and runs nothing. Any other program that answers the dialog (an app built on the Agent SDK, a custom prompt tool) is refused; one of the owner's own account that passes itself off as the extension or the app is not told apart, and neither is an Agent SDK app started from the extension or the app that keeps running after it (`nohup`, a process manager). In `auto` mode the dialog needs Claude Code 2.1.211 or later, read from the running Claude Code; where it cannot be read, the refusal says what was tried, and the owner switches the permission mode to default. A session never runs the command on its own, as a test, or after a refusal. When `go` stops with exit 8 it prints the facts for the owner (what the writes do, why, the blast, the undo, the stop reason, what was checked) and the two commands to run on the owner's go; where the session cannot open the owner's dialog (no Claude Code session, a `-p` run, something that can answer the dialog in place of a human), it prints why and, in place of a sign command the hook would refuse, the path that works: queue the run here (`go --queue`), the owner signs it inside a `claude` session in a terminal (`/vibemaestro-sdlc:owner-sign`) and this session runs it (`run --queued <id>`), or `go` runs there; the hook's and `sign`'s refusals for those reasons name the same path, and the mode question says where the owner answers; in a sandbox pod it prints the hand-off instead (pack as `project:`, open the PR, hand over the call: name, args, seal) and no `sign` or `go --queue` is run; `rehearse` there prints no sign command. A seal that no longer matches what was shown is refused. **No dialog shown, or a rejected one, means not confirmed**: the session records the run as pending and says so; it never retries `sign` in a loop and never reads silence as a yes.

**A run the owner did not answer.** A kit baton that asks the owner for a secret during its run (its header declares `Stops: secrets`) ends its run phase with exit 75 and the last line `VERDICT run unanswered` when no answer came in time and it wrote nothing before the ask. When the owner signed that run (a record in `signatures/`) and its undo passes, the runner gives the signature back: the spent record is linked back to `signatures/<binding>.json`, never over a record already there, the log line's result is `unanswered <k>/3`, and the run's report says to run the same call again. The rerun is checked as any run (the script bytes, the values, the directory, the variables that steer the tools and the plan), so a changed call needs a new signature, and it asks again from the start. A signature comes back at most 3 times per owner dialog, counted from the records of that dialog in `used/` (one per run), so a new signature of the same call counts from 0. Every other run spends its signature as before: another exit or last line, a failed undo, a fourth time, a session, `kind:`, `project:` or `user:` baton, a kit baton without `secrets`, a queued item, a run signed by the session or under a plan approval (its use stays taken). The exit code is 4, as for any run its undo put back.

**The owner's queue.** An open dialog holds the session that asked until the owner clicks, and its record lives 30 minutes. When the owner is away, the session runs `go --queue <script> [args…]` instead of `go`: the same check, rehearse and seal, then an item in `<state-dir>/queue/<id>.json` (private) that holds the seal, the arguments as given and as bound, the directory, the script's sha256, the plan, the decision card, the session and the Claude Code process that queued it, the time and an expiry 24 hours later, and a sha256 over all of it. It prints one line naming the item and the session goes on working; `log --wait-queued <id>`, run in the background, ends when the item is signed. The owner signs at the time they choose, in the session that queued the item or another Claude Code session: `/vibemaestro-sdlc:owner-sign` lists the pending items (`log --queue`) and runs `sign --by owner --queued <id>` once per item they pick, alone in its Bash call; the hook opens the dialog, which shows the item's card, and writes the record as for `--seal`. The signature goes into the item and names its sha256. The session that queued an item signs it through this dialog like any other, also after `/clear`: the owner's click is the signature in every session. `run --queued <id>` runs a signed item once, from the directory it was queued in, before it expires: its rehearse must give the sealed plan (a moved head, base or file is a refusal), then run, post-check and log as `run`. An item whose bytes changed after the dialog opened or after signing, an expired one, an unsigned one and a used one are refused. An item that will never run is withdrawn, kept and marked who, when and why: `queue withdraw <id> --reason <word>` from the session that queued it (unsigned only), or the owner's `sign --by owner --void <id>`; the owner also voids a signature that never ran with `sign --by owner --void <binding>`, which moves the record to `voided/` so no run matches it; `kit:plugin-update` prints that command for each item it waits on. Like the signature records, an item guards against slips, not against a process of the same user that rewrites both the item and its signature. A baton whose `Stops` names `secrets` is never queued: `go --queue` refuses it right after check (exit 64), before rehearse, an item or a signature, because a secret is given only to a `run` or `go --row` phase and a queued run gets none; it runs through `go` with the owner's dialog, or `go --row`. Mode `manual` and `auto`, the stop list and a pod are as above: a pod queues nothing and never signs as the owner.

**Plan approvals.** A plan row declares the trust-layer changes its pull requests make, in its `Trust touches` cell: `none`, or `;`-separated items. A touch is `<kind> [<owner/repo>:]<path> [<object>] [Stops: <words>]`, the repository defaulting to the plan's own: `script`, `baton` (with its `Stops:` as `stops_of` reads them, `removed` for a deleted baton), `workflow`, `rbac`, `admission` and `vault-policy` (each naming the rendered object `<Kind>/<namespace or ->/<name>`), `config` (under `.vibemaestro/`), `other <exact path> [<object>]` (one file, or one object a touch check names, that no other kind fits; never the path `-`) and `test <path>` or `test <directory>/` (test data by its path: under a `tests` or `test` directory with no `templates`, `batons`, dot or agent directory above it, not `*.sh`, Markdown, an agent or a secret-file name; a directory covers every such file under it). `run <kit:name or project:name> Stops: <words> [runs: <n>]` declares a baton run (never a `user:` baton, a session file or a `kind:`), `PRs: <n>` how many pull requests use the row (1 to 20, 1 when absent, as `runs:`), and a touch may end in `(signs again)`. A path is exact and case-sensitive, with no glob: a glob admits a file nobody named. The floor is never covered by a plan, so a touch on it must end in `(signs again)` or the dialog refuses it: a path that judges a later pull request (the config, an adapter it names, the planner's script and inputs, every `merge.touch_inputs` path, `.vibemaestro/risk-tier.yaml`, `.vibemaestro/gates/`), a path with a `.claude-plugin` segment at any depth and in any case, a baton whose Stops drop a word of `SIGN_AGAIN_STOPS` (`security-boundary`, `irreversible-delete`, `no-way-back`, `history-rewrite`) that its default branch holds (a deleted baton drops none), a run whose Stops hold one, and a `secrets` run of any baton outside `PLAN_SECRETS_KITS` (the list below). The owner signs a plan once: the session writes an approval spec, a JSON file of `plan` (1 to 20 different plans, each pinned by `{repo, path, commit}`) and `expires` (UTC, at most 30 days ahead), and runs `sign --by owner --approve <absolute path of the spec>` alone in its Bash call; it covers every row that is not dropped (a spec that still lists `rows`, each `{plan, row}`, covers those rows only). The hook reads each plan at its commit through `gh api`, with the intent and the spec its `Intent:` and `Spec:` line names (one of each), the spec's acceptance criteria (the numbered items of its `## Tiêu chí chấp nhận` or `## Acceptance criteria` section), each touch repository's config and each declared baton's Stops on the default branch, then opens the dialog. Its card lists the project directory, the expiry, each plan with its intent's and spec's sha256 and the criteria (only their count past 2048 bytes or 40 items), every row with its touches and PRs (a baton's Stops on the default branch beside the declared ones), what signs again and why, and the runs whose value, file or passphrase the owner types on the passphrase holder's page. It is denied, each reason named, for a plan with no intent or spec, a spec with no criteria, a row that is not in the plan at that commit, is `dropped:` there, has no `Trust touches` cell or shares its id with another row ignoring case, and for a touch that is a glob, of an unknown kind, the path `-`, or the floor unmarked (with a record, `sign` refuses such a spec, exit 64). The click writes `<state-dir>/grants/<id>.json` (`kind: approval`, `v: 2`: the plans, their intent and spec paths and sha256, the criteria, each row's cells but its Link cell with its parsed touches; no code, so a plugin update leaves it in force) and a `grant signed` log line, bound to the project directory it was signed from; it is in force only while its file is intact and that line names its body, and a past expiry, a revoke file or a `grant revoked` log line ends it; `log --grants` lists it with each row and how many of its pull requests merged, and `grant revoke <id>` ends it. It runs nothing itself: `kit:merge-pr` merges under it and `go --row` runs under it (below). Signing again makes a new approval that cannot merge a row past the uses its PRs allow, nor run a baton past the runs its touch allows.

`PLAN_SECRETS_KITS`, the kit batons whose `secrets` runs a plan covers (each asks the owner on the passphrase holder's page in its run, or runs only reviewed code): `vault-put-text`, `vault-put-file`, `credential-import`, `credential-upload`, `kubeconfig-install`, `script-run`, `script-run-upload`.

**Merges under an approval.** `kit:merge-pr` reads approvals only where the base's `merge.touch_checks` names a check; `merge.touch_inputs` names, for each, the workflow file that runs it and every path its result depends on, and a touch check with no `touch_inputs` entry makes the config invalid (exit 65). The kit names `signing-rules`, its workflow, the gate and what it imports (`gate_common.py`, `baton.py`); the gate keeps its list as a constant and runs from the base checkout, so there is no list file and no pin. The guard's condition `touches` then judges each trust-layer change of the pull request: each path the deny globs match (a rename's source too), its kind by a fixed table (`baton`, `workflow`, `config`, `script`, `test`, else `other`), and each finding of a touch check whose latest runs are all red, read from the artifact `trust-touches` of its workflow run (`trust-touches v1` or `v2`). A touch check's conclusion is its workflow run's, so a token that rewrites a check run does not turn it green (a check run that says success over a cancelled or still running workflow run fails `checks` and `required`). Each change must be a touch of the row the pull request's body names (exactly one line `plan: [<owner/repo>:]kb/plans/<name>.md#<row>`; any other line that starts `plan:`, such as the CI planner's `plan: 8/45 suites`, is not a plan line and is ignored), under an approval in force signed from the directory the merge runs from, on repository, path (a `test` directory covers every file under it), kind, object and Stops, as the approval holds them; the row must be one row of the plan, not dropped, on the plan's default branch and, when the pull request is in the plan's repository, at its head, and there the intent and the spec must have the sha256 the approval holds and the row every cell it held but its Link cell (a new row, a Link cell or a Decisions line changes nothing signed; anything else is "the plan changed since the owner signed it": sign it again); earlier merges may have used the row fewer times than its PRs, whatever commit or approval named it. Never covered, whatever a row declares or marks: the floor (a path that judges a later pull request, a path with a `.claude-plugin` segment, a signing-rules finding of kind `other`, a baton whose head drops a `SIGN_AGAIN_STOPS` word its Stops hold at the base tip), a touch the row marks `(signs again)`, a finding the check could not judge or judged a secret (`owner-merge`), the `other` of a `trust-touches v1` block (where those read the same), a kind no row declares, the path `-`, a run of that check's name another workflow file made, and a red touch check with no artifact, no `end` line, a wrong count or `end 0`. So `other` is covered from a denied path or a `v2` finding only. A path with a `.claude-plugin` segment, at any depth and in any case, is also denied by the guard itself in every lane, whatever `merge.deny_globs` says (in bootstrap it is never a scaffold path; in the image-bump lane it fails `lane-deny`). When every change is covered, deny and the red touch check pass and the plan line says `touches:<approval>/<row>`, so the session's signature binds it; otherwise `FAIL touches` names each change and why, and the owner merges. The run takes one of the row's uses (a `touches used` log line and a marker under `touches/`; either one counts) right before the merge call, with `O_EXCL`, so two merges cannot both take the row's last use, and a merge call GitHub refuses still spends it: that pull request is then the owner's merge. A red required check that is not a touch check stays `FAIL checks`, and a pending, skipped or cancelled touch check stays `FAIL required`: neither is a trust-layer change the row could declare.

**Runs under an approval.** In the coordinator's session on the owner's machine, `go --row [<owner/repo>:]kb/plans/<file>.md#<row> <baton> <args>` checks and rehearses as `go`. Where `go` would stop for the owner (exit 8), it runs the baton when all of these hold, else it exits 8 naming the first that does not: an approval in force, signed from this project directory, holds the row (of the one repository whose plan holds it, when the line names none); a `run` touch of the row names the baton; the touch is not marked `(signs again)` and is not the floor; the baton's Stops, its header's as it reads at run time (with `security-boundary` for a value that names a settings file), hold no `SIGN_AGAIN_STOPS` word and `secrets` only for a kit baton of `PLAN_SECRETS_KITS`, and lie within the touch's Stops (`none` declares none); a `project:` baton is reviewed (its bytes the blob on origin's default branch, origin on the owner's remote list, section 4; a keep record alone is not enough, and bytes neither pinned here nor reviewed stop before, exit 3, as for `go`); the touch has a run left of its `runs: <n>`; and the plan is as signed at its repository's default branch, read through `gh api`: the row there and not dropped, its cells but its Link cell, the intent and the spec, as the approval holds them (a read that fails is no match). No code is bound, so a plugin update between the signature and a run (a move, or new bytes with the same Stops) changes nothing. The match is signed in that process only, `plan:<approval>/<row>/<n>` (`n` counts that baton's runs under the row), over the call's binding as `go` read it: bytes or arguments that change before the run phase are refused (exit 3). Right before the run phase the call is matched again and use `n` is taken: a marker under `touches/` created with `O_EXCL` and a `touches used` log line, keyed by the plan's repository and path, the row and the baton, never the commit, so two runs at once cannot both take the last use and an approval signed again counts the uses already taken. The run then leaves its spent record in `used/<stamp>-<pid>-<binding>.json` in the shape an owner-signed run leaves (`v: 2`, the binding, the script's path and sha256, the arguments, the directory, the variables that steer the tools, the plan and its sha256, the Stops), with `signed_by: plan:<approval>/<row>/<n>` and `approval: <id>` in place of a dialog id: what the passphrase holder reads to serve such a run. The run, its post-check and its undo are those of any run, and the use stays taken whatever the result. A `user:` baton, a session file, a `kind:` and stdin never run under a plan (exit 64), and nothing does in a sandbox session.

**The passphrase hold.** A run under an approval whose Stops hold `secrets` may need the GPG passphrase of a key. The passphrase holder asks the owner once per approval, keeps the passphrase for at most 24 h (and never past the approval), and serves it to the approval's later runs, so the owner types one passphrase per approval, not one per run. A `kit:script-run` run is closed to the hold when its script starts: nothing the script starts can take the passphrase; a handover's token hold, after the script, asks the owner again. `log --digest` lists, under each approval (and each charter), that hold's lines from the `holds.tsv` the passphrase holder writes, the one such file in a directory beside the baton state, in the window (`open`, each `serve` with the run it served, `refuse`, `close`, `end`; never a value), and says in one line when the file is absent or unreadable, or has lines it cannot list, and when two or more directories beside the baton state each hold one (none is read).

**Focus charters.** A charter is the owner's one signature for a focus of the brain (an open `P<n>`), not for one plan: `sign --by owner --charter <spec>`, the spec a JSON object of exactly five keys, at most 64 KiB, given by an absolute path: `focus` (a focus the brain installed beside this plugin shows live through `brain show <P> --json`, as intake reads it, with its `done when`), `repos` (1 to 10 `owner/name`, none twice), `kinds` (a non-empty subset of `baton`, `workflow`, `script`, `test`: any other kind stays with a plan approval or the owner's merge), `max_stops` (stop words; `owner-acts` and the `SIGN_AGAIN_STOPS` words are refused, and `[]` means touches and runs with no Stops) and `expires` (a UTC time after now, at most `CHARTER_LIFE_MAX`, 90 days, ahead). It takes the same hook, dialog, one-use record, `grants/` store, `grant signed` log line and project-directory binding as `--approve`. The card shows the focus with its goal, the owner's quote and where (`Quote:`; for a focus the session opened, whose brain item holds no owner's quote and where, or a blank one, the line `opened by the session` stands in its place: nobody said those words), its `done when` and, when it has one, its `not doing`; the repositories, kinds, maximum Stops and expiry; what it covers, what never (the floor, and every touch outside the envelope) and what the owner types. The record (`kind: charter`, v 1) binds the focus, the sha256 of its words as the card showed them (`focus_sha256`), the envelope and the directory. Words or a spec changed after the dialog are refused (exit 3); a spec that breaks a rule, a closed or unknown focus, a focus with no `done when`, or a second charter for a focus from the same directory or another worktree of its repository while one is in force (named) are refused with exit 65. To change the envelope, `grant revoke <id>` and sign again. `log --grants` lists charters, `grant revoke` ends one, and `grant revoke --focus <P>` ends each one in force for that focus signed from this project: the brain's `op close` of a focus runs it before it writes the close, and refuses the close when they cannot be revoked; `op supersede` of a focus does the same, since it ends that focus too (the owner signs again for its successor). A charter is never read as an approval, nor the reverse, and an older version of the plugin never treats one as in force: a mix of versions fails closed, to an owner merge.

**Merges and runs under a charter.** `kit:merge-pr`'s guard and `go --row` read the approvals first, so nothing an approval covers stops being covered; where none covers, they read the charter in force for the `focus:` of the plan's frontmatter, signed from the project directory they run from (that very directory, as for an approval). A plan with no `focus:` is read as before. The plan is read with no pinned commit, at its repository's default branch; that repository must be one of the charter's `repos`, and the plan line's path must be written plainly (a `.` or `..` part names the same file to GitHub under another use key: refused). A merge is covered when the plan says that focus at the default branch's tip and, when the pull request is in the plan's repository, at its head; the row is one row of it on both sides, not dropped, with the same cells but its Link cell (a pull request cannot widen its own row: "row moved in this PR"); a use is left of its `PRs` (the uses merges took under an approval count, and the reverse); and every trust-layer change is a touch of the row, as under an approval, inside the envelope: its repository in `repos`, its kind in `kinds`, its Stops within `max_stops` (a deleted baton has none). The floor and a touch marked `(signs again)` are never covered. The plan line then says `touches:charter-<id>/<row>` and the `touches used` line is signed `charter:<id>`; otherwise `FAIL touches` names each part outside, and the owner merges. `go --row` reads a charter only for a plan line that names its repository (`<owner/repo>:kb/plans/<file>.md#<row>`); a line with none reads approvals only. Under a charter it runs the baton when the row, at the default branch's tip and not dropped, has a run touch naming it that covers the call as under an approval (not marked, not the floor, declared or at run time, the Stops within the touch's, a `project:` baton reviewed, a run left) and the baton's Stops lie within `max_stops`. The run is signed `plan:<charter id>/<row>/<n>`, and its spent record holds `charter` (the id) and `touch` (the run touch, with the plan's path and the row) in place of `approval`, so the passphrase holder reads no plan. A charter past its expiry, revoked, or whose focus the brain closed covers nothing.

**The owner's delegation window.** A window is a W item the owner pins in vibemaestro-brain through the brain's own owner dialog, with a scope: `brain owner add --kind window … --expires <time> --lower <word>… [--exclude <word>…]`, each word a stop category or a kit baton by name (`kit:<name>`), at most 8 of each, the expiry at most 24 hours ahead. While it is in force, a `go` or a `sign --by coordinator-auto` that mode `auto` would stop only for the baton's declared Stops is signed `coordinator-auto` with no dialog when the window covers it: every Stops word is one the window lowers, or the baton is a `kit:` it names, and none is one it excludes. Only for the session that pinned it (its subagents, and the same session after a compaction or `--continue`, share its id; `/clear` and `--fork-session` start a new one). Never lowered, whatever a window says: `secrets`, `cluster-lane`, `irreversible-delete`, `history-rewrite`, `money-org`; the batons that change the machine's own permissions (`kit:bootstrap` and its old name, `kit:permissions-upgrade`, `kit:plugin-install`, `kind:settings-merge`), any call whose value names a Claude Code settings file, `security-boundary` of a baton that is not a `kit:` one (its body may write the settings), and an owner merge (`kit:owner-merge`) of a pull request that changes the signing floor: a file of `WINDOW_FLOOR_PATHS` in `scripts/baton.py`, the files that decide who signs and what a window may lower (the runner and its guards and launcher, the scripts that run the hooks (`pyrun.sh`), the signing-rules gate, its job, its lists and the copy that would shadow the runner, the merge guard and the merge config, the brain's owner guard and window code, the owner merge itself), any path under `.vibemaestro/` of the pull request's repository (its gate config, vendored gates and project batons), and a file under `batons/` or `templates/baton-kinds/` that is modified, removed or renamed (an edit of a baton's Stops changes who signs it; a new baton is not on the floor), the old name of a renamed file too, read from GitHub's file list of each pull request (a list that cannot be read, or one at GitHub's 3000-file cap, stops the call); a worker session, mode `manual`, `go --row` and `go --queue`. The brain refuses such a scope before its dialog, and the runner enforces it. The brain is the one record: the runner keeps no copy and reads the session's brain at each signature and each run (`brain windows --json` of the brain installed beside this plugin, which folds the brain's log once its whole hash chain is verified, never a cache). So the owner's `brain owner unpin W<n>`, the session's `brain op close W<n> --reason <why>` (no dialog: it only narrows) or the expiry ends it at once, and a run signed under a window that no longer covers it is refused (exit 3), nothing run. With no brain, a broken chain, no live window with a scope, or a clock behind the newest time in the brain's log or the runner's, signing is as with no window. Closing a window spends none of the session's retirement budget. The signature record holds `window` (its id, times and scope), the `sign`, `run-start` and `run` lines of `log.tsv` name the signer `coordinator-auto@W<n>`, `go`'s one line ends `— window W<n>`, and `log --digest` lists those runs under `window W<n> of the brain`. Where a live window does not cover a call, the exit-8 card adds `window: not lowered: <why>`. A window differs from a plan approval: it lists no steps, binds no plan or arguments, and lasts a day at most; each run under it is still checked, rehearsed, sealed and signed for its exact call, and only the owner's click is replaced.

**The decision card.** Right before the owner's dialog the session writes, in the owner's language, at most seven short lines: what it writes, where, why (the decision or the need), the impact, the undo (or "cannot be undone"), the one risk, and what was checked (check ok, rehearse ok, plan matches Expect, N writes). The `sign` command's description, which the dialog shows, is the card's first line; seals, paths and the rehearse output come after, as detail.

## 7. Cost

**What was measured.** Sending every write through a run costs more than the direct way: over an 18-task session, a session that sends every write through BatonRun costs 3.05 to 3.67 times a session with no plugin per correct write, with no break-even within the 18 tasks, and doing a kind of write a second time gains no more with BatonRun than without, because most batons were written anew each time. The per-task part dominates: the session writes about 4.4 to 4.9 times the output tokens. Correctness was the same in both arms. The method and the numbers are in [`docs/research/batonrun.md`](../../../docs/research/batonrun.md).

**What follows from it.** A simple write is a direct call, not a run, so it costs what the direct way costs. A flow met before is not written again: `baton list` finds the kept baton and one `go` with new values runs it, with no skill read and no script written. The checks are machine checks and cost almost nothing; the cost is model turns and output kept in context, which is why `go` exists, why it prints one line, and why the skill is read only to write or change a baton. What keep-and-call saves over writing anew is not measured yet.

**Running several runs.** In place by default, any number. Hand three or more to one worker subagent only to keep a large main context small (over about 400k tokens): delegation is cheaper only for a session's first multi-run task. The main session then waits on the log for the exact script names (`log --wait-names`), and trusts the log line, which is machine evidence, not the worker's report.

## 8. Limits

What baton does not guard:

- **Honest, not hostile.** BatonRun guards a fallible session, not a deceiving one (section 1); editing an approval file and `log.tsv` together is forgery too (section 6). `check` reads the text; it does not run it, so an indirection that hides a run (`eval`, a name built at run time, a launcher behind a variable) is forgery, not a gap to work around.
- **The rule and its launcher warning advise; they do not block.** The rule reminds once per session when a privileged command is typed directly, on the command line only. The hook warns on every launcher `sign`, `run` or `go` that is not bare (a pipe, a chain, a redirect, a substitution, a prefix or a shell wrapper), because the allow rules then do not match and Claude Code's auto-mode classifier decides.
- **Permission rules match the command text,** not what the shell makes of it, and Edit rules cover the write tools and the file commands Claude Code recognises, not any process. `permissions --check` reads the rules only: not `defaultMode`, a skip-permissions launch, or the classifier's settings.
- **A plugin script is trusted from the plugin root `baton.py` runs from,** only as the command of a write with its sha256 in the plan line; a `scripts/` changed during a phase is detected after it, not prevented.
- **What `go` cannot tell:** whether a fresh file holds what was meant (an Edit that did not apply), and anything about a file the script reads itself unless its sha256 is in a plan line.
- **A mode comes from the owner, not from a message.** A session cannot tell another agent or machine to change its approval mode, or its remote list.
- **"Reviewed" trusts the local view of origin.** A reviewed project baton is checked against `refs/remotes/origin/HEAD`, a local ref, at the baton's path from the repository's top, and against the URL git fetches origin from (`git remote get-url origin`, after `insteadOf`); that git runs without the caller's `GIT_*` variables. Moving the ref by hand (`git update-ref`, a fetch from another URL than the one checked) is forgery, as editing the state directory is.
- **`go -` with a baton is blocked by Claude Code.** In the default permission mode (tested with Claude Code 2.1.303, `-p --permission-mode default`, allow rule `Bash(<launcher> go:*)`) the allow rule matches a short `go -` heredoc, but a heredoc holding the baton skeleton is blocked before any rule applies, by the tool's own check ("Contains brace with quote character (expansion obfuscation)"), which fires on every `{ … }` function body that holds a quote (`write()`, `gh_state()`). Auto mode is not tested. Default is a supported mode, so the standard does not depend on auto: a session baton is a Write to a fresh path and `go <path>`. The check is the tool's safety check; the skeleton is not reshaped to dodge it. The hook stays silent on a quoted `go -` heredoc, though that is blocked for a baton, and names every other shape (an unquoted delimiter lets the shell expand the body before baton reads a byte; a line after the closing one is a command of its own).
- **A value is safe in the shell, not in every tool.** A `Params` value reaches the script as one argv word of a checked type: it cannot end a shell word, start an option or add a plan line. A tool that reads its own code or files from it can still misread it; `check` refuses a value in `eval`, a heredoc body, a command name, `gh -F` and `curl -d`, and the skill's `limits.md` names the safe forms for the rest (`jq --arg`, `gh -f`, `--` before operands, no value inside a `sed`, `awk` or `find -name` program). Free text from outside goes through an `input` file, never the command line. A secret goes through a `path` value, never a `file` or `input` value, which is copied and kept: one that looks like key material is refused (exit 64). A `path`, `under:`, `file` or `input` value is refused (exit 64) when the last segment of its path, the basename, starts with `-`, `+` or `@`; a middle segment may.
- **A flow split into simple writes is not seen.** Nothing tells a flow cut into single writes from honest single writes; the rule and the skill name the cut as the thing not to do.
- **The settings guard finds; it does not prove.** It reads Bash as text. It does not see a name built at run time (a variable, `$(…)`, string glue, a glob without `settings` in it), a script file run, a baton the session wrote (`check` flags its writes onto a settings path as `security-boundary`, and a call whose argument names a settings file stops for the owner, section 6), `git apply`, `git am`, an archive unpacked, a checkout or merge that does not name the file, a directory copied whole over `.claude`, a write through a link made earlier under another name, an MCP tool that writes files, a write on another host (`ssh host '…'`), or the app state file `~/.claude.json`. It also denies a `python -c` that reads the settings and writes another file, a `.claude/settings*.json` that Claude Code does not read (a backup, an example, a test fixture), and a writer word after a runner that is only an argument (`sudo grep rm .claude/settings.json`). A settings file with comments counts as not JSON.
- **A plan approval pins where, not what.** `touches` checks repository, path, kind, object and Stops; what a declared file does is the review's to read, and the spec's acceptance criteria are the pull request's evidence to show. The `plan:` line is the session's claim, so the review and the post-check confirm the pull request serves its row, and the row's PRs bound the harm to that row's touches. A run touch names a baton and its Stops, never its arguments: the session chooses them, and `log --digest --plan <id>` lists every run. Editing an approval file and `log.tsv` together is forgery.
- **A merge, a publish and the like cannot be undone.** The run says so in `Undo:`; when it fails after the world changed it ends with exit 5 and the owner is told at once.
- **`signing-rules` reads uses, not behaviour.** It sees how a list is used in its own file, not what a plain read leads to, a condition, a baton's body or code in another file that reaches the list. The workflow that runs it comes from the pull request, so an edit to it is an owner merge through `merge.deny_globs` (`.github/workflows/**`), not through the gate. A crafted change passes it, for example a run-time reach it does not list (an aliased `exec`, `builtins`, a frame's globals, `getattr` on a module), a list wrapped in a container and mutated through it (`([X] * 1)[0].clear()`), or an object whose own method changes its argument (`join`, `__add__`).

## 9. Permission setup

Once per machine, the session runs three commands and the owner applies the result; the plugin never writes settings:

1. `permissions --install-launcher` copies the launcher to `<state-dir>/bin/baton`. It runs the newest installed vibemaestro-sdlc from the plugin cache and refuses any other `baton.py`. Run it from the installed vibemaestro-sdlc, the one the registry (`installed_plugins.json`) lists: a cache copy the registry no longer lists (a session started before a plugin update) refuses with exit 10 and writes nothing.
2. `permissions --print` prints the user-settings block; the owner adds it through Claude Code's settings.
3. `permissions --check` says whether the rules in force hold the split (exit 0) or names each rule that is missing, stale or unsafe (exit 7). A session whose vibemaestro-sdlc is not the installed one gets one line instead, naming both versions: restart Claude Code (exit 10).

The kit run `kit:bootstrap` can do steps 1 and 2 in one run the owner signs (skill `bootstrap`).

**After a plugin upgrade.** An upgrade needs nothing while the installed launcher copy can run the new version: it picks the registry's latest entry. When it cannot (a copy installed before the version directories named after a git commit refuses them all), every baton is refused until step 1 runs again from the installed vibemaestro-sdlc, then step 3. The check names that case first, and so does SessionStart, before the first baton fails; `kit:plugin-update` prints both steps itself after it updates the plugins. A session started before the update still runs the older plugin: its check says restart Claude Code, and never offers that plugin's launcher.

**The split.** Allow the launcher's `new`, `check`, `rehearse`, `run`, `go`, `list`, `pack`, `log` and `sign --by coordinator-auto`. Ask for `sign --by owner` and `mode`, in every spelling of the command. Deny Claude Code's write tools on the whole plugins directory of the Claude Code config (the cache and `installed_plugins.json` the launcher trusts) and on the state directory. The same block turns Claude Code's attribution off (no co-author trailer, no PR line, no session URL).

**Why it is safe.** `run` is gated by the signature. `coordinator-auto` is refused by `baton.py` itself outside mode `auto` and for any run whose `Stops` is not `none`, so the session can sign only what the owner's standing rule already allows. The owner's signature and the mode always open a dialog. An allow rule on a command is only as safe as what it runs is unwritable, which the deny rules keep. The rules name the launcher because a permission rule cannot match "any version" in the middle of a path. SessionStart says in one line when the check fails.
